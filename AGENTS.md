# Project instructions

- Keep Cargo mutation snapshots and normal qualification builds in separate mutable target directories. Restoring source text does not establish that a cached library/executable is unmutated. After an accidentally shared cache, invalidate the owned package with Cargo, rebuild, and run negative contracts against the final linked executable before collecting evidence. Retain failed/cache-contaminated attempts as unavailable source-correspondence evidence rather than passing qualification.

- For each numerical solver checkpoint on the Windows Intel development host, run `scripts/Test-IntelCircuits.ps1` with a trusted `SPICE_INTEL_HOST` alongside affected solver tests; retain the low-level `Run-ParallelProbe.ps1 -Probe Intel` check too. `scripts/Test.ps1` includes both gates. Report actual device, numerical comparison, test scope and unavailable evidence; self-test-only runs, CPU fallback and missing hardware do not establish GPU coverage. The optional Intel adapter is experimental; whole-deck comparisons remain separate from the bounded routine checks. Keep outputs on E: and follow the resource/watchdog policy before launching workloads.

- Before substantial additional parser/solver/model implementation, apply the canonical reuse-before-build gate. Evaluate complete existing solutions, including SpiceSharp/SpiceSharpParser and ngspice integration, rather than limiting the search to Rust crates. Record concrete gaps and executable evidence; do not treat the current language/architecture choice as proof that reuse is unsuitable. An evaluation does not itself authorize a production migration.

- Read `docs/implementation-plan.sdoc`, `docs/architecture.sdoc` and `docs/development-standards.sdoc` before implementation.
- Use C# or F# for scripts/automation by default and PowerShell cmdlets for shell/text/file operations. A required tool runtime, such as StrictDoc's Python runtime, is an explicit exception rather than a default scripting choice.
- Keep authoritative requirements in StrictDoc with stable IDs and honest implementation/test evidence links. Update `backlog.json` from the plan when work-package metadata changes.
- Comment public interfaces, ownership, units, numerical assumptions, invariants and non-obvious logic meaningfully; update comments alongside code.
- Collect actual line/branch coverage where supported, report exclusions and unavailable metrics, and apply relevant mutation, malformed-input, fuzz and randomized/property tests with reproducible seeds and minimized failures.
- Keep parsing, immutable circuit/plan structures, model evaluation, numerical controllers, backend adapters, runtime and results separated as specified. No legacy simulator runtime dependency in the product core.
- C#/F# and GUI code consume the public API, not internal solver/model state. Definition DSL evaluation does not run in the Newton/device hot loop.
- Do not promise arbitrary solver combinations, universal GPU acceleration, native-code sandboxing from Rust alone, universal convergence or compatibility without qualification evidence.
- Deliver the next evidence-backed vertical slice from the plan rather than creating all proposed crates or adapters at once. Do not infer completed work from planning documents.
- When resuming an active qualification goal, inspect the current worktree, requirements, evidence, and handoff prompt before acting. Preserve the goal's full scope, make concrete verified progress, and leave it active unless completion or the documented blocked audit is proven.
- Maintain the repository as a careful long-term steward: prefer small reversible commits, keep the handoff material accurate, and thank contributors respectfully for their guidance and trust.
- Never commit build outputs, runtime environments, credentials, downloaded native binaries or large fuzz/benchmark corpora. Record reproducible acquisition instructions and immutable hashes when those assets become necessary.

- Store new build/generated outputs, coverage, mutation/fuzz/soak data, downloaded tools and temporary test data under the existing E: artifact root on this Windows host (CODEX_ARTIFACT_ROOT when configured). Use a unique checkout/run subtree and supported tool output settings. Keep source on its existing filesystem, preserve active/unknown artifacts, and do not assume NTFS capabilities on exFAT.

## Memory policy — latest canonical user rules, 2026-11-16

Before memory-intensive tests, builds, benchmarks, fuzzing or long jobs, arm and confirm a watchdog with explicit process-tree runaway limits and an aggregate concurrent-job budget. Size limits for the installed machine and expected workload, bound concurrency, preserve OS/interactive headroom, and log full-tree termination and observed usage on breach. Windows manages paging: never gate startup or terminate work based on free/available RAM; it is telemetry only. Identify owned processes and descendants positively, preserve unrelated projects and active campaigns, and retain failures or incomplete outcomes honestly. Keep simulator input bounds, deadlines, cancellation, locks and E: artifact routing. This replaces the older project no-cap exception after the user's canonical rules update. Historical evidence retains the policy actually used when it ran.
- Qualification must bind the actual executable path/hash, build profile and enabled features to tested source. An output directory named release or an unchanged-source gate alone is insufficient. Invoke the existing Run-RequestedCorpus entrypoint with explicit engine arguments; avoid selecting executables by path-string replacement.
